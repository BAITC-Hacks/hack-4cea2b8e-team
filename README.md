## 1. Что решает

AML-аналитику банка известен только нижний уровень цепочки — 81 клиент,
получавший деньги. Кто собирает эти деньги, через кого их прогоняют и кто ими
распоряжается, он восстанавливает вручную: часы работы на один узел, при том
что реальная сеть — 2 248 узлов.

Инструмент за минуты даёт ранжированный список узлов с обоснованием роли
каждого. Фокус проверки смещается с 81 «курьера» на реальные точки
консолидации.

## 2. Что реализовано

- Сборка направленного графа переводов из выгрузки
- Метрики по каждому узлу: плательщики, получатели, обороты, коэффициент пропуска
- Присвоение роли по документированным правилам с объяснением
- Кластеризация сети и гипотеза по каждому кластеру
- Ранжированный топ-лист приоритетов для аналитика
- Экран просмотра сети с направлением потоков, подсветкой ролей и поиском по gid

## 3. Запуск

```bash
git clone <URL>
cd <папка>
pip install -r requirements.txt
python -m pipeline.run --data data/ --out out/
```

Пайплайн отрабатывает за `<N>` секунд и создаёт три файла в `out/`.
Экран просмотра:

```bash
uvicorn app.main:app --port 8000   # http://localhost:8000
```

Требования: Python 3.11+, без GPU, без облака, без платных сервисов.

## 5. Критерии ролей

Все пороги собраны в `THRESHOLDS` в `pipeline/roles.py` — одно место, никаких
магических чисел по коду. Пороги подобраны по реальным распределениям
(`python scripts/explore.py --data data/`).

| Роль | Правило | Порог |
|---|---|---|
| `coordinator` | принимает от многих и раздаёт многим | `<...>` |
| `consolidator` | много плательщиков, удерживает значимую часть | `<...>` |
| `distributor` | веерная отправка многим получателям | `<...>` |
| `transit` | пропускает почти всё полученное дальше | `<...>` |
| `terminal` | деньги приходят и остаются | `<...>` |
| `peripheral` | устойчивых признаков не выявлено | — |

Каждый узел получает `evidence` — обоснование с конкретными числами из данных,
понятное аналитику без ML-образования. Чёрного ящика нет: любую роль можно
объяснить, посмотрев на метрики узла.

Формулировки намеренно осторожные — «признаки консолидации», а не «организатор».
Выводы подаются как гипотезы для проверки, а не как утверждение о виновности.

## 6. Учёт особенностей данных

| Особенность | Как учтена |
|---|---|
| Обрыв обхода на последнем колене: узлы с `depth=4` и нулевыми исходящими — это граница выгрузки, а не «деньги осели» | Флаг `truncated`. Такие узлы не получают роль `terminal`; в `evidence` прямо сказано, что нужна выгрузка на колено глубже. Наивное правило `out_degree == 0 → terminal` дало бы сотни ложных срабатываний |
| Видны только исходящие переводы | Полный баланс узла не считается |
| У seed занижены входящие — граф собран от них | Флаг `ratio_reliable`; коэффициент пропуска для seed не применяется |
| Порог 5 000 ₸ | `<как учтено / оговорка>` |
| Часть seed без исходящих переводов | Обрабатываются как отдельный случай при обходе |
| Сеть не монолитна: несколько слабосвязных компонент | Номер компоненты в метриках, кластеризация не смешивает их |
