# Граф денег

Инструмент для AML-аналитика: строит направленный граф переводов, определяет
объяснимые гипотезы ролей и показывает, кого проверять первым и почему.
Все выводы относятся к наблюдаемой выборке и не являются утверждением о виновности.

HackAlem AI, 23.09.2026. Команда «Калифорнийское бюро расследований»:
Аяган Елнур, Кайсарбеков Аргын, Пермин Константин.

## Подготовка и запуск

Python 3.11 или 3.12; проверено на Python 3.12. GPU, Node.js, облако,
API-ключи и платные сервисы для анализа не нужны. Команды ниже — для macOS/Linux.

```bash
git clone https://github.com/BAITC-Hacks/hack-4cea2b8e-team.git
cd hack-4cea2b8e-team
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
```

Поместите предоставленные организаторами `edges.parquet`, `nodes.parquet`
и `transactions.parquet` в `data/`. Данные не включены в Git и не скачиваются
приложением. Все последующие команды выполняются из корня репозитория.

**Один запуск от исходных файлов до выгрузок:**

```bash
python -m pipeline.run --data data --out out
```

**Запуск экрана на реальных данных без внешнего LLM:**

```bash
DEMO_MODE=1 python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Откройте **http://127.0.0.1:8000/graph.html** (также `/graph`). Корень `/`
содержит старый стартовый экран и не является экраном расследования.
`DEMO_MODE=1` отключает внешнюю модель в стартовом LLM-модуле; граф при этом
всегда рассчитывается из parquet и не заменяется демонстрационными данными.
Остановка сервера — Ctrl+C.

Проверка сервера: `http://127.0.0.1:8000/api/health`, ожидаются
`graph_loaded: true`, `n_nodes: 2248`. Спецификация API: `/docs` и `/openapi.json`.
`/docs` — вспомогательная Swagger-страница с внешними ресурсами; для автономной
проверки используйте `/openapi.json` или [контракт API](app/API.md).

### Автономная работа

После установки Python-зависимостей и получения данных пайплайн и
`/graph.html` работают без интернета. Vue 3.5.22 и vis-network 9.1.9
поставляются в `web/vendor/` и загружаются с локального сервера; npm и CDN
во время запуска не используются. Системные шрифты, SVG-иконки и стили локальные.
Для проверки отключите интернет, оставьте сервер работающим и перезагрузите
`/graph.html`: поиск, фильтры и операции должны продолжать работать.

Первоначальная установка пакетов обычно требует интернета. Для установки
на изолированную машину заранее на машине с теми же ОС, архитектурой и версией
Python подготовьте wheel-пакеты:

```bash
python -m pip download --only-binary=:all: -r requirements.txt -d wheelhouse
```

Перенесите репозиторий, данные и `wheelhouse` на целевую машину и установите:

```bash
python -m pip install --no-index --find-links=wheelhouse -r requirements.txt
```

Значимые настройки: `DATA_DIR` — каталог данных для HTTP API,
`DB_PATH` — путь SQLite стартового приложения. CLI использует собственный
аргумент `--data`. После замены parquet сервер нужно перезапустить.
Ошибка схемы или несовпадение агрегатов с транзакциями отклоняет набор,
а не подменяет данные. Если при старте набор отсутствует или повреждён, сервер
остаётся доступен для загрузки; графовые API отвечают 503 до успешной загрузки. При занятом порте задайте `--port 8001` и измените URL.

## Загрузка через браузер

Можно запустить сервер без parquet в `data/`, открыть `/graph.html` и нажать
«Загрузить данные». Для замены существующего набора используйте кнопку ⇧
в панели графа или откройте `/upload.html`.

Выберите edges, nodes и transactions в соответствующих полях формы,
нажмите «Загрузить и построить граф», дождитесь результата и перейдите к графу.
Каждый файл должен быть непустым parquet размером до 100 МиБ. Проверяются
схемы, согласованность трёх таблиц и возможность полного расчёта.

Файлы сначала записываются в отдельную временную папку и анализируются.
При ошибке активный граф и файлы не меняются. Успешный набор сохраняется
в `DATA_DIR/.uploads/<dataset_id>/`, указатель `DATA_DIR/.active-dataset`
переключается атомарно. Первоначальные parquet и предыдущие версии остаются
на диске. Сервер восстанавливает последнюю активную версию после перезапуска.
История версий пока не удаляется автоматически; режим рассчитан на один
локальный процесс сервера без `--workers`.

CLI читает явно указанный каталог и не следует указателю автоматически.
Для экспорта загруженного через браузер набора при стандартном `DATA_DIR=data`:

```bash
python -m pipeline.run --data "data/.uploads/$(cat data/.active-dataset)" --out out
```

Эта команда используется только после успешной загрузки. HTTP-экспорт всегда
относится к активному набору. Страница загрузки также работает с локальным Vue
и не обращается к CDN. Подробнее: [контракт загрузки](app/API.md).

## Вход и выход

Вход — три таблицы за июль 2026:

| Файл | Обязательные поля | Объём данных трека |
|---|---|---:|
| edges.parquet | src, dst, sum_kzt, n_tx, depth | 3 119 рёбер |
| nodes.parquet | gid, depth, is_seed | 2 248 клиентов |
| transactions.parquet | src, dst, date, sum_kzt | 4 840 операций |

| Результат | Содержание |
|---|---|
| out/nodes_roles.csv | gid, role, role_score, cluster_id, priority_score, evidence, typologies |
| out/clusters.csv | cluster_id, n_nodes, n_seed, sum_kzt_internal, top_gids, hypothesis |
| out/top_nodes.csv | rank, gid, role, priority_score, why, typologies; по умолчанию топ-25 |
| out/resilience.json | дополнительная оценка удаления топ-25 из графа |

`typologies` — расширение базовых схем ТЗ, значения разделены `|`.
При строгой проверке фиксированных колонок это расширение требует согласования;
текущая реализация его сохраняет. `top_gids` также разделены `|`.
В CSV gid сохраняются целыми int64; в JSON — строками, поскольку значения
превышают точность JavaScript Number. Никогда не преобразуйте gid в Number.
CSV доступны также через `/api/export/nodes_roles.csv`, `/api/export/clusters.csv`
и `/api/export/top_nodes.csv`.

## Критерии ролей

Источник правил и порогов — [pipeline/roles.py](pipeline/roles.py).
Правила проверяются **в порядке таблицы**, назначается первая подходящая роль.
`P` — число разных плательщиков, `R` — число разных получателей,
`K = sum_out / sum_in`. `ratio_reliable` истинно только для не-seed,
не-обрезанного узла с положительными наблюдаемыми входящими.
Это разрешение использовать отношение в эвристике, а не гарантия полноты баланса.

| Порядок / роль | Формальное правило | role_score |
|---|---|---:|
| 1. peripheral — граница | depth ≥ 4 и нет исходящих | 0,20 |
| 2. coordinator | P ≥ 5 и R ≥ 5 | 0,70 |
| 3. consolidator | P ≥ 8, ratio_reliable, K ≤ 0,5 | 0,80 |
| 4. distributor | R ≥ 20 | 0,80 |
| 5. transit | ratio_reliable, 0,8 ≤ K ≤ 1,2 | 0,75 |
| 6. terminal | ratio_reliable, K ≤ 0,1, sum_in ≥ 1 000 000 ₸ | 0,75 |
| 7. peripheral | остальные случаи | 0,30 |

`role_score` — заданная эвристическая оценка правила, не калиброванная вероятность.
`evidence` содержит метрики и объяснение до 200 символов. Пороги исходные,
ориентированы на структуру данных и требуют валидации аналитиком; размеченных
ролей нет, accuracy не заявляется. Отсутствие признаков не означает отсутствие риска.

## Приоритет проверки

```text
priority_score = 0,5 × вес роли
               + 0,3 × (sum_in + sum_out) / максимальный оборот клиента
               + 0,2 × (P + R) / максимальное число связей клиента
```

Вес роли: coordinator 1,0; consolidator 0,9; distributor 0,7;
terminal 0,6; transit 0,5; peripheral 0,1. При нулевом максимуме соответствующее
слагаемое равно нулю. Результат округляется до 4 знаков; сортировка по убыванию,
при равенстве — по gid. API карточки возвращает `priority_breakdown` с тремя
слагаемыми. `why` в CSV объясняет роль; формула выше объясняет ранжирование.

Текущий топ-25 содержит 18 coordinator, 4 consolidator и 3 distributor.
Перекос связан с порядком правил и весом роли, а не доказывает наличие
18 организаторов. Для улучшения нужны проверка пересечений правил,
чувствительности к порогам и экспертная оценка; выравнивание числа ролей
ради внешнего вида не является обоснованной настройкой.

## Типологии и кластеры

Типологии независимы от основной роли, один клиент может иметь несколько:

| Признак | Правило |
|---|---|
| structuring | ≥4 перевода одной пары; коэффициент вариации сумм ≤0,35; весь период этой пары ≤7 дней |
| layering | ≥70% наблюдаемых входящих сопоставляются с исходящими за 0–2 дня; FIFO без повторного расходования суммы |
| synchronized-inflow | ≥3 разных плательщиков в один день |
| round-tripping | участие в направленных циклах длиной до 4 |

Это сигналы для проверки. Layering не доказывает многоступенчатое сокрытие;
циклы не доказывают возврат тех же денег. Точное время внутри дня неизвестно.
Дробление ниже 5 000 ₸ невидимо; правило повторных сумм может пропустить
короткий всплеск внутри длинного периода активности пары.

Кластеризация — взвешенный Louvain с seed=42 на неориентированной проекции;
встречные суммы складываются. Изолированные клиенты сохраняются.
Внутренний оборот включает только рёбра внутри сообщества. Гипотеза кластера
строится по составу ролей, а не по внешним сведениям о клиентах.

## Сценарий аналитика и демо на 5 минут

1. Запустить пайплайн, показать три CSV и время расчёта (около минуты демо).
2. Открыть `/graph.html`, выбрать клиента из топа или ввести полный gid.
   Поиск по префиксу предлагает варианты. Сверить обоснование с метриками.
3. Нажать на стрелку: изучить сумму, число переводов и «Показать операции».
   Нажать gid отправителя/получателя для продолжения. «Назад» возвращает клиента.
4. Проверить ещё два разных случая: seed с «Н/Д» и узел на границе выгрузки.
   Объяснить, почему отсутствие исходящих не равно доказанному удержанию денег.
5. Показать фильтры ролей/кластеров, кнопку «Показать кластер» и ограничения.

Иконка обозначает роль; число справа сверху — входящие плюс исходящие операции
в выборке, не число соседей. Полный gid виден при наведении/выделении и в карточке.
Прямые стрелки сохраняют направление перевода; после построения узлы неподвижны.
Разрешены перетаскивание и масштабирование. Подграф ограничен 150 узлами;
сообщение об ограничении означает, что часть окружения не показана.
Карта не является полным досье или автоматически доказанной цепочкой денег.

## Общая сводка сети

Кнопка «Сводка» открывает показатели всей активной выгрузки: число участников,
операций, суммы, распределение ролей, 10 крупнейших связей, примеры клиентов
каждой роли и крупнейшие потоки между ролями. «Подробнее» раскрывает таблицы,
«Свернуть» возвращает компактный вид, крестик или Escape закрывают панель.
Ссылка gid открывает выбранного клиента на графе. «Обновить» запрашивает
актуальный `/api/summary`; фильтры окружения не меняют общие показатели.
После загрузки нового набора переход к графу загружает новую сводку.
В другой уже открытой вкладке обновите страницу, чтобы и граф, и сводка
относились к одному набору. Входящие и исходящие — две стороны тех же переводов;
их нельзя складывать как уникальный оборот.

## Ограничения и производительность

- 444 узла на границе обхода не классифицируются как terminal.
- У seed входящие неполны: отношение потоков скрывается и не используется
  для правил консолидации, транзита или конечного получателя.
- 19 изолированных seed сохраняются; всего 31 seed без исходящих.
- Видны только внутрибанковские операции ≥5 000 ₸ за один месяц.
  Нет ФИО, ИИН, остатков и внешних источников; атрибуты не выдумываются.
- В итоговом графе 35 компонент: 16 с рёбрами и 19 изолированных клиентов.
  Это объясняет отличие от числа 16 в описании связанной части данных.
- Нет AI-ассистента, который отвечает по графу на естественном языке.
  Стартовый `/api/generate` не подключён к данным расследования.
- Нет авторизации и журнала действий аналитика: сервер предназначен для
  локального демо на 127.0.0.1, не для размещения банковских данных в интернете.
- Подграфы могут быть перегружены; фильтры скрывают связи, а не удаляют их из данных.

На предоставленной выборке: 2 248 клиентов, 91 кластер, 25 строк топа.
Локально на Python 3.12 расчёт внутри CLI занимал 0,8–4,3 секунды
(без установки пакетов); это замер на рабочей машине, не гарантия для любого
оборудования. Лимит ТЗ — 5 минут. Код не требует GPU и внешних вызовов.

## Масштабирование до миллиона узлов

Текущая реализация хранит pandas-таблицы, NetworkX-граф и API-карточки в памяти
и пересчитывает их при старте. На миллионе узлов такой подход не проверен.
План развития, а не уже реализованные возможности:

1. Хранить операции в Parquet по датам; агрегировать пакетно через DuckDB/Polars
   или SQL, учитывать объём рёбер и транзакций, а не только число клиентов.
2. Перенести графовые расчёты на компактные массивы/CSR и igraph либо другой
   движок с измеренным потреблением памяти. Сначала измерить RAM и время.
3. Выполнять метрики и сообщества фоновыми заданиями, сохранять версию результата;
   API читает подготовленные данные и индексированные соседства.
4. Пересчитывать изменившиеся метрики инкрементально, сообщества — периодически.
   Нормировка рейтинга глобальная: обновление максимумов требует согласованной версии.
5. Ограничить поиск циклов компонентами и бюджетом, индексировать даты для
   временных паттернов: перечисление циклов может резко вырасти на плотном графе.
6. Передавать в браузер агрегаты сообществ и ограниченные подграфы с пагинацией,
   а не миллион точек. Добавить отмену запросов, кэш и замеры задержек.
